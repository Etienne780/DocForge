# DocForge — File Formats

This document lists every file DocForge reads or writes, describes what each one contains and
records how each format changed from one app version to the next. It is meant for people who
write or edit these files by hand and for tools that read them, so it can be used without
knowing the code. Code references (in `code`) are only pointers for contributors.

For the internal data model in more detail, see [DEV_REFERENCE.md](DEV_REFERENCE.md) §15 (Data
Shapes) and §16 (Persistence, Envelopes & Migration).

## 1. Overview

All DocForge files are UTF-8 JSON (2-space indented when DocForge writes them), except the
Markdown entry files of folder projects.

| Extension / file | Contains | Envelope `kind` | Current schema | Since app version |
|---|---|---|---|---|
| `.dfproj` | A whole project in one file | `project` | 4 | 1.0.0 |
| `.dftheme` | One doc theme (look of the preview and the HTML export) | `theme` | 2 | 1.0.0 |
| `.dflang` | One syntax definition (code highlighting of a language) | `language` | 1 | 1.0.0 |
| `.dflangstyle` | One highlight style (token colors for a language) | `languageStyle` | 1 | 2.3.0 |
| `.dfapptheme` | One app theme (colors of the DocForge interface) | `appTheme` | 1 | 2.4.0 |
| `docforge.config.json` | Structure of a folder project | – (no envelope) | follows the project schema | 2.0.0 |
| `docforge.README.md` | Generated format guide of a folder project, never read back | – | – | 2.4.0 |
| `tabs/*/*.md` | Content of one entry of a folder project | – | – | 2.0.0 |

Double-clicking or dropping a `.dfproj`, `.dftheme`, `.dflang`, `.dflangstyle` or `.dfapptheme`
file opens it in DocForge (`main/fs/ProgrammArgs.js`, `renderer/core/FileImportManager.js`).

## 2. The envelope

Since 2.0.0 every JSON file DocForge writes (except `docforge.config.json`) is wrapped in an
envelope (`renderer/core/Envelope.js`):

```json
{
  "kind": "project",
  "storageVersion": 4,
  "data": { }
}
```

| Field | Meaning |
|---|---|
| `kind` | What the file contains, see the table above |
| `storageVersion` | Schema version of `data`, see [§6](#6-version-history) |
| `data` | The actual content |

When reading, a file **without** an envelope (no `data` key) is treated as schema version `0`
and the whole object is used as the data. This is how files from 1.x are opened.

Some exported files carry an extra key **next to** the envelope keys (`styles` in `.dflang`,
`languages` in `.dftheme`). Readers that only look at `data` can ignore them.

## 3. User files

IDs are strings generated by DocForge (`<prefix>_<random>`, e.g. `node_lf3k2def4`). Timestamps
are milliseconds since 1970 (`Date.now()`). Unknown fields are dropped on load, and missing
fields are filled with defaults, so a hand-written file only needs the fields it cares about.

### 3.1 `.dfproj` — project

`kind: "project"`. Written when a project is saved as a single file and by "Export project".
An export leaves out `id`, `createdAt`, `sourcePath` and `sourceKind`; DocForge creates new
IDs when it imports a project anyway.

```jsonc
{
  "kind": "project",
  "storageVersion": 4,
  "data": {
    "id": "project_lf3k2abc9",
    "name": "My Project",
    "createdAt": 1710000000000,
    "tabs": [ /* Tab */ ],
    "themes": [ /* DocTheme, see 3.2 */ ],
    "languages": [ /* SyntaxDefinition, see 3.3 */ ],
    "languagesStyles": [ /* HighlightStyle, see 3.4 */ ],
    "links": [ /* Link */ ],
    "settings": {
      "isThemePreset": true,         // true: currentThemeId is a built-in theme
      "currentThemeId": "theme_Dark",// null: fallback theme
      "formatGuide": { "enabled": false, "preferences": "" },
      "tabSize": 2                   // 1-16
    }
  }
}
```

**Tab**

```jsonc
{ "id": "tab_…", "name": "Documentation", "nodes": [ /* Node */ ] }
```

**Node** (an entry; nodes form a tree through `children`)

```jsonc
{
  "id": "node_…",
  "name": "Getting started",
  "content": "# Getting started\n\n…",  // Markdown, LF line endings
  "type": "page",                       // "page" | "folder" | "merged"
  "mergeDescendants": "embed",          // "embed" | "separate", only for type "merged"
  "children": [ /* Node */ ]
}
```

**Link** (reference link, used as `[[slug]]` in the Markdown)

```jsonc
{
  "id": "link_…",
  "slug": "getting-started",                       // [a-z0-9-], unique in the project
  "name": "Getting started",                       // link text
  "target": { "nodeId": "node_…", "anchor": null },// anchor: null = whole entry, else the name of {#name}
  "refs": [ "node_…" ]                             // entries that use the link, kept up to date by DocForge
}
```

### 3.2 `.dftheme` — doc theme

`kind: "theme"`. Written by "Export theme" and as `themes/*.dftheme` in folder projects.

```jsonc
{
  "kind": "theme",
  "storageVersion": 2,
  "data": {
    "id": "docTheme_…",
    "name": "Dark Teal",
    "builtIn": false,
    "createdAt": 1710000000000,
    "lastOpenedAt": 1710000000000,
    "settings": {
      "entries": [
        { "name": "accent", "value": "#22d4a8", "active": true }
        // one entry per theme setting
      ],
      "langStyleIds": {
        "<language id>": { "id": "<style id>", "isBuiltIn": true }
      }
    }
  },
  "languages": [ /* optional, export only: .dflang objects, see 3.3 */ ]
}
```

- `entries` holds colors, sizes, fonts and layout options. The full list of names and their
  allowed values is `THEME_SCHEMA` in `renderer/data/DocThemeManager.js` (summary in
  DEV_REFERENCE §10, Theme Schema). Entries that are missing get their default value, and
  entries DocForge doesn't know are removed. `active: false` means "use the fallback".
- `langStyleIds` picks the highlight style per language for this theme.
- `languages` (since 2.3.0, exports only): project languages chosen in the export dialog, each
  with its styles. On import they get new IDs and `langStyleIds` is remapped to them.

### 3.3 `.dflang` — syntax definition

`kind: "language"`. Written by "Export language" and as `languages/*.dflang` in folder projects.

```jsonc
{
  "kind": "language",
  "storageVersion": 1,
  "data": {
    "id": "syntaxDefinition_…",
    "name": "C++",
    "aliases": [ "cpp", "c++" ],        // code fence names that use this language
    "builtIn": false,
    "createdAt": 1710000000000,
    "lastOpenedAt": 1710000000000,
    "exampleCode": "",
    "symbolHoisting": false,
    "rootStateId": "syntaxState_…",
    "states": [ /* SyntaxState */ ],
    "predefinedSymbols": [ { "name": "std", "tokenType": "namespace" } ]
  },
  "styles": [ { "style": { /* HighlightStyle */ }, "refs": { } } ]  // optional, export only
}
```

A language is a state machine: each **state** has a list of **rules**, the first rule that
matches wins. Rules are of type `match` (regex, keyword list or word), `beginEnd` (a region
between two patterns, optionally with its own inner state) or `include` (the rules of another
state). The full shape of states, rules and actions is in DEV_REFERENCE §15
(SyntaxState / SyntaxStateRule); the token types and enums are in DEV_REFERENCE §11.

`styles` (since 2.3.0, exports only) carries the highlight styles chosen in the export dialog.
Folder projects never write it.

### 3.4 `.dflangstyle` — highlight style

`kind: "languageStyle"`. Written by "Export language style" (since 2.3.0).

```jsonc
{
  "kind": "languageStyle",
  "storageVersion": 1,
  "data": {
    "style": {
      "id": "highlightStyle_…",
      "langId": "syntaxDefinition_…",
      "name": "Default",
      "tokenStyles": [ { "tokenType": "keyword", "color": "#c678dd", "bold": false, "italic": false, "underline": false, "underlineStyle": null } ],
      "stateTokenStyles": [ { "stateId": "…", "tokenType": "…", "color": "…", "bold": false, "italic": false, "underline": false } ],
      "overrides": [ { "stateId": "…", "ruleId": "…", "style": { /* token style */ } } ]
    },
    "refs": { "langName": "C++", "states": { }, "rules": { } },
    "language": null
  }
}
```

- `refs` stores the **names** of the language, states and rules the style refers to. Built-in
  languages get new state and rule IDs on every app start, so on import the style is matched
  by these names, not by ID.
- `language` is the custom language the style belongs to, as a full `.dflang` envelope, or
  `null` for built-in languages.

### 3.5 `.dfapptheme` — app theme

`kind: "appTheme"`. Colors of the DocForge interface itself, not of the documents. Written by
the export of the app theme in the preferences, and on desktop as the storage of custom app themes
(see [§5](#5-internal-app-data)). Since 2.4.0.

```jsonc
{
  "kind": "appTheme",
  "storageVersion": 1,
  "data": {
    "id": "apptheme_…",
    "name": "My theme",
    "baseId": "nord",                     // built-in theme used for missing colors and "reset"; may be null
    "colors": {
      "dark":  { "background": "#2e3440" },// CSS variable name without "--" -> CSS color
      "light": { }
    }
  }
}
```

Variable names must match `^[a-z][a-z0-9-]*$` and values must be strings, other entries are
dropped. A color that is missing falls back to the `baseId` theme, then to the DocForge default.
The editable variable names are listed in `APP_THEME_GROUPS` (`renderer/data/AppThemeManager.js`).
An imported file always becomes a new custom theme with a new ID.

## 4. Folder projects

A folder project (desktop only, since 2.0.0) stores a project as a folder, so it can be
versioned with Git and edited with other tools.

```
<project folder>/
  docforge.config.json     structure: settings, tabs and entry tree, no content
  docforge.README.md       generated format guide (only if enabled, since 2.4.0)
  themes/
    <name>.dftheme         one per project theme (see 3.2)
  languages/
    <name>.dflang          one per project language (see 3.3)
  tabs/
    <tab name>/
      <entry name>.md      one per entry, flat, regardless of the tree depth
```

Folder and file names are the tab and entry names made filesystem-safe; duplicates become
`Name (2)`. The chosen name is stored as `folderName` / `fileName`.

### `docforge.config.json`

Plain JSON, **no envelope and no `storageVersion`** (see [§7](#7-compatibility-rules)):

```jsonc
{
  "id": "project_…",
  "name": "My Project",
  "settings": { /* as in .dfproj */ },
  "languagesStyles": [ /* HighlightStyle */ ],
  "links": [ /* Link */ ],
  "tabs": [
    {
      "id": "tab_…", "name": "Documentation", "folderName": "Documentation",
      "nodes": [
        { "id": "node_…", "name": "Intro", "fileName": "Intro", "type": "page", "children": [] }
      ]
    }
  ]
}
```

Themes and languages are not listed here; they are read from their own folders.

### Entry files (`tabs/<tab>/<entry>.md`)

Markdown with a small front matter block for the ID and the name (line breaks in the name are
written as spaces):

```md
---
id: node_lf3k2def4
name: Intro
---

# Intro
```

### How DocForge reads a folder

What is on disk wins over the config:

- Entry files are matched to the config tree by `folderName` / `fileName`, not by ID.
- An `.md` file that the config doesn't list is added at the root of its tab. Its ID comes from
  the front matter, or a new one is created if there is none.
- A folder under `tabs/` that the config doesn't list becomes a new tab named after the folder.
- Every `*.dftheme` / `*.dflang` file is loaded; the file name doesn't matter, the ID is inside.
- On save DocForge deletes `.md`, `.dftheme` and `.dflang` files and tab folders that no longer
  belong to the project. `docforge.README.md` is only deleted if it starts with the marker
  `<!-- docforge:format-guide - generated by DocForge, do not edit -->`.

So adding an `.md` file or a tab folder by hand and reopening the project is enough for it to
show up.

## 5. Internal app data

These files belong to the app and are not meant to be edited. They are listed so that support,
backups and debugging know where to look.

### Location

| Platform | Where |
|---|---|
| Desktop | `<userData>/data/<slot>.json`. `<userData>` is Electron's user data folder, e.g. `%APPDATA%\DocForge` (Windows), `~/Library/Application Support/DocForge` (macOS), `~/.config/DocForge` (Linux) |
| Web | `localStorage`, key `docforge:<slot>` |

Development builds use their own data: `<userData>/data/dev/…` and `docforge:dev::<slot>`.
A `:` in a slot name becomes a subfolder on desktop (`backups:index` → `data/backups/index.json`).

### Slots

| Slot | Envelope `kind` | Schema | Contains |
|---|---|---|---|
| `state` | `state` | `UI_STATE_SCHEMA_VERSION` 1 | Preferences and UI state (dark mode, editor mode, app theme ID, shortcuts, …). Keys: DEV_REFERENCE §2 |
| `recentProjects` | `recentProject` | `RECENT_PROJECT_SCHEMA_VERSION` 1 | Recent projects: `{ id, name, lastOpenedAt, sourcePath, sourceKind }`. On web `sourceKind` is `in-app` and the entry holds the whole project as a `project` envelope |
| `projectPresets` | `projectPresets` | `PRESET_PROJECT_SCHEMA_VERSION` 2 | Templates saved by the user: `{ id, name, description, createdAt, projectVersion, project }`. `projectVersion` is the project schema the snapshot was saved with |
| `themePresets` | `themePresets` | `PRESET_THEME_SCHEMA_VERSION` 1 | Doc themes saved by the user as templates (DocTheme objects) |
| `backups:index` | – | `BACKUP_VERSION` 2 | `{ version, projects: [{ fileId, projectKey, projectName, sourcePath, lastBackupAt, resolvedAt }] }` |
| `backups:<fileId>` | – | `BACKUP_VERSION` 2 | `{ version, slots: [{ id, date, label, data: { project: <project envelope> } }] }`, newest first, at most 10 |

### App themes

Desktop: every custom app theme is one `.dfapptheme` file (see 3.5) in
`<userData>/app-themes/<id>.dfapptheme`. Web: custom app themes only live for the session.

## 6. Version history

Each format has its own schema version (`*_SCHEMA_VERSION` in `renderer/core/AppMeta.js`). It
only changes when the shape of the data changes, not with every app release. The migration
code that upgrades old data lives in `renderer/migration/`, one file per format.

### At a glance

| App version | Project | Theme | Language | Lang. style | App theme | UI state | Recents | Project presets | Theme presets | Backups |
|---|---|---|---|---|---|---|---|---|---|---|
| 1.0.0 – 1.3.0 | 0 | 0 | 0 | – | – | – | – | – | – | – |
| 2.0.0 – 2.1.0 | 2 | 2 | 1 | – | – | 1 | 0 | 0 | 0 | 1 |
| 2.2.0 | 2 | 2 | 1 | – | – | 1 | 1 | 1 | 1 | 1 |
| 2.3.0 | **3** | 2 | 1 | **1** | – | 1 | 1 | **2** | 1 | 1 |
| 2.4.0 | **4** | 2 | 1 | 1 | **1** | 1 | 1 | 2 | 1 | **2** |

`0` = no envelope yet. `–` = format didn't exist. Bold = changed in that version.

1.x kept its internal data (UI state, recent projects) in an older format that 2.0.0 doesn't
read. Projects from 1.x had to be exported as `.dfproj` and imported again; the user files of
1.x (`.dfproj`, `.dftheme`, `.dflang`) are still read today.

### Project (`.dfproj`, `docforge.config.json`) — `ProjectMigration.js`

| Schema | App version | Change |
|---|---|---|
| 0 | 1.0.0 | No envelope. The file is `{ project, theme }` with one optional theme next to the project |
| 2 | 2.0.0 | Envelope. The theme moved into the project (`themes[]`, `settings.isThemePreset`, `settings.currentThemeId`); `languages[]` and `languagesStyles[]` were added; folder projects were introduced. Schema 1 was never written |
| 3 | 2.3.0 | Entries got `type` (`page` \| `folder` \| `merged`, old entries become `page`) and `mergeDescendants`; projects got reference `links[]` |
| 4 | 2.4.0 | `settings.formatGuide` (`{ enabled: false, preferences: '' }`) and `settings.tabSize` (old projects get 2) |

### Doc theme (`.dftheme`) — `ThemeMigration.js`

| Schema | App version | Change |
|---|---|---|
| 0 | 1.0.0 | No envelope |
| 2 | 2.0.0 | Envelope, data unchanged. Schema 1 was never written |

New theme settings are added in most releases without a schema change: missing `entries` get
their defaults on load. Since 2.3.0 an exported theme can carry `languages` (see 3.2).

### Syntax definition (`.dflang`) — `SyntaxDefinitionMigration.js`

| Schema | App version | Change |
|---|---|---|
| 0 | 1.0.0 | No envelope |
| 1 | 2.0.0 | Envelope, data unchanged |

Since 2.3.0 an exported language can carry `styles` (see 3.3).

### Highlight style (`.dflangstyle`) — `LanguageStyleMigration.js`

| Schema | App version | Change |
|---|---|---|
| 1 | 2.3.0 | New format |

### App theme (`.dfapptheme`) — `AppThemeMigration.js`

| Schema | App version | Change |
|---|---|---|
| 1 | 2.4.0 | New format. The doc editor colors of earlier versions (`editorColors` in the UI state) are turned into a custom app theme "My editor colors" on the first start |

### Internal data

| Format | Schema | App version | Change |
|---|---|---|---|
| UI state | 1 | 2.0.0 | Envelope |
| Recent projects | 1 | 2.2.0 | Envelope (`RecentProjectMigration.js`) |
| Project presets | 1 | 2.2.0 | Envelope (`PresetProjectMigration.js`) |
| Project presets | 2 | 2.3.0 | Presets got `description`, `createdAt` and `projectVersion`; old presets run every project migration step |
| Theme presets | 1 | 2.2.0 | Envelope (`PresetThemeMigration.js`) |
| Backups | 1 | 2.0.0 | All backups in one `backup` slot |
| Backups | 2 | 2.4.0 | One slot per project (`backups:<fileId>`) plus `backups:index`; old backups are moved on the first start |

## 7. Compatibility rules

- **Newer DocForge reads older files.** Every format is migrated step by step from its stored
  schema version to the current one when it is loaded. Files from 1.x can be opened in 2.x.
- **Older DocForge does not reliably read newer files.** There is no downgrade path; fields an
  older version doesn't know are dropped when it saves.
- **Unknown fields are removed, missing fields get defaults** on load. Hand-written files can
  be minimal.
- **Folder projects have no version number.** `docforge.config.json` stores no
  `storageVersion`, so every project migration step runs on each load. Steps must therefore
  keep values that are already in the new shape.
- **IDs inside a file are not stable across import.** Importing a project, theme, language,
  style or app theme gives it new IDs; references inside the file are remapped.

## 8. Keeping this document up to date

When a persisted shape changes (see `CLAUDE.md` and DEV_REFERENCE §16):

1. Bump the matching `*_SCHEMA_VERSION` in `renderer/core/AppMeta.js` (once per release) and add
   the migration step.
2. Update the shape in [§3](#3-user-files) to [§5](#5-internal-app-data).
3. Add a row to the format's table in [§6](#6-version-history) and update the overview table.

A new file type also needs: a `FILE_EXTENSION_*` constant in `AppMeta.js`, an entry in
`main/fs/ProgrammArgs.js` and `FileImportManager.js`, a `fileAssociations` entry in
`package.json`, an entry in `hooks/AfterPack.js` (macOS) and an icon in `assets/icons/<ext>/`.
